# 評測計畫：主導模型 × Jev × 派工 × 工具

狀態：**已登記**（2026-10-15，使用者同意；登記版本＝把本行改成「已登記」的那個 commit，`git log -S'已登記' -- docs/eval-plan.md` 可查）。之後任何改動都寫進文末「變更紀錄」，
寫明改了什麼、為什麼、是在看到哪些結果之前或之後改的。對應 `docs/decisions.md` 的 D4。

## 0. 為什麼要重做

使用者回報：昨天用過 jevcc 的 agent 都指出，artifact 和 README 裡的節省數字是作者自己量的，別人不知道怎麼用、怎麼測，
也無法確認自己會有一樣的效益。檢查現有評測後發現：

1. **沒有隔離**：`jevcc bench` 的 `claude -p` 沿用執行者的 `~/.claude`（`internal/bench/bench.go` 的 `cmd.Env = append(os.Environ(), ...)`），
   所以作者裝的 plugin、hook（包含全域的 jevcc 本身）、CLAUDE.md 都進了每一組。別人的環境不同，數字自然對不上。
   實測（2026-10-15，Claude Code 2.1.300，一句 `reply ok`）：init 事件顯示載入了 3 個 SessionStart hook、7 個 plugin
   （superpowers、claude-dashboard 等）、5 個 MCP server、79 個 skill，以及使用者的自動記憶目錄。
2. **題目沒有鑑別力**：`bench/tasks` 的 10 題在 2026-10-14 的紀錄中 opus 和 haiku 都是 100% 通過（`bench/results/bench-20261014-113723.md`），
   README 的「省 97%」就是在這組題目上量的。題目難不倒便宜模型時，「同品質更便宜」是必然結果，不能推論到一般工作。
3. **難題沒有對照**：`bench/hard` 有 haiku 0/10 的紀錄（`bench-20261014-140103.md`），但沒有 opus 在同組題目上的結果。
4. **只有程式題**：品質全靠確定性檢查，開放式工作（影片、設計、規劃、研究）完全沒有量。
5. **`+14%` 查不到出處**：「往下派工多花 14%」只剩 `internal/hook/hook.go` 的說明字串。

## 1. 要回答的問題

- **Q1** 同一批工作，opus／sonnet／haiku 各自主導，品質和成本差多少？依工作類別分開回答。
- **Q2** 開 Jev 並往上派工（便宜模型主導、難題交給強模型），能把品質差距補回多少？多花多少？
- **Q3** 開 Jev 並往下派工（強模型主導、執行交給便宜模型），能省多少？品質掉多少？
- **Q4** `jev-*` subagent 的工具限制（現狀）和工具全開，成本與品質差多少？（決定 D3）
- **Q5** 每一類工作，品質與成本的最佳組合是哪個？「同品質下最便宜」或「同成本下品質最好」。

不回答：Jev 路由本身的準確率（已有 `jevcc eval`）、guard／inject 等其他功能。

## 2. 組別

### 2.1 因子

| 因子 | 值 |
|---|---|
| 主導模型 | opus、sonnet、haiku（實際模型 ID 從每次執行的 `modelUsage` 記錄） |
| Jev | 關、開 |
| 派工方向（Jev 開時） | 往上、往下、雙向（定義見下） |
| subagent 工具 | 限制（現狀 `Read, Grep, Glob, Bash, Edit, Write`）、全開（省略 `tools`） |

派工方向的定義：

- **往上**＝jevcc 的預設行為，也就是一般使用者裝了就會得到的：做事途中難題交給 `jev-<更強>`（escalate），
  回合結束時若改了程式且 Jev 判斷有風險，交給 `jev-review`（opus）檢查（Stop review）。兩者在 `config` 中預設都開。
  Stop review 目前只在改了程式碼時才會觸發，開放式題目大多不會觸發，報告會分開列出觸發次數。
- **往下**＝`"delegate": true`：主導模型把簡單的部分交給 `jev-<更便宜>`。
- **雙向**＝兩者都開。

### 2.2 不存在的組合

opus 主導沒有更強的模型可以往上派；haiku 主導沒有更便宜的可以往下派。報告中這兩格標「不適用」，不是缺資料。

### 2.3 分三階段跑（不做全因子交叉）

| 階段 | 組別 | 組數 | 回答 |
|---|---|---|---|
| 1 基準線 | opus、sonnet、haiku 主導，Jev 關、不派工 | 3 | Q1 |
| 2 Jev 與派工 | opus＋往下；sonnet＋往上／往下／雙向；haiku＋往上（工具維持現狀） | 5 | Q2、Q3、Q5 |
| 3 工具 | 階段 2 中有派工的組別，工具限制 vs 全開，只跑需要 MCP 或 skill 的題目 | 最多 10 | Q4 |

每階段開始前看上一階段結果，但**只能用來決定要不要跑下一階段，不能改本階段的題目或判定方式**。

### 2.4 主要比較與探索性比較

比較的組合很多，純靠機率也會有幾組「看起來有差」。事先指定**主要比較**，報告的結論只建立在這些上面；其他都標「探索性」。

1. 每類工作：haiku 主導 vs opus 主導、sonnet 主導 vs opus 主導（Q1）。
2. 每類工作：haiku＋往上 vs opus 主導（Q2：往上派工能不能用更低成本達到 opus 主導的品質）。
3. 每類工作：opus＋往下 vs opus 主導（Q3）。
4. 需要 MCP／skill 的題目：工具全開 vs 限制（Q4）。

## 3. 題目

### 3.1 類別

| 類別 | 題數（目標） | 例子 | 確定性檢查 |
|---|---|---|---|
| A 程式（易） | 沿用 `bench/tasks` 10 題 | 找檔、改名、修 off-by-one | 現有檢查 |
| B 程式（難） | 沿用 `bench/hard` 5 題 | cron、expr、ledger、lru-ttl、semver | 隱藏測試 |
| C Blender（MCP 操作） | 3 | 產品展示場景：物件、材質、三點打光、攝影機、渲染 640×360 | headless bpy 讀出場景（物件、材質、燈光、攝影機參數）＋輸出圖檔存在且尺寸正確 |
| D 導演／影片（Remotion） | 2 | 依 fixture 裡的 README 做 20–30 秒專案介紹影片 | ffprobe 長度與解析度、字幕覆蓋率、`blackdetect` 找黑畫面、無字幕空檔 |
| E 設計 | 2 | 帶限制條件的系統設計（含刻意埋的衝突需求） | 必要段落存在；埋的衝突有被點出（關鍵字清單） |
| F 規劃 | 2 | 依規格寫專案計畫：相依、風險、里程碑 | 必要段落存在；隱藏的關鍵風險清單命中數 |
| G 研究（固定資料集） | 2 | 給 8–12 份文件，回答需要綜合比較的問題，附引用 | 每個引用都能在資料集中找到原文（可用 `jevcc cite` 邏輯） |
| H 方向不明確 | 每類 C–F 各 1 題變體 | 「做一個讓人想用這個工具的介紹」 | 同所屬類別 |
| S 需要 skill | 2 | 資料集附一個 skill，題目要照 skill 的規範做才會過 | 輸出符合 skill 規範 |

C、S 兩類是階段 3 的主要題目。H 類是為了量「定方向」：題目寫得越清楚，越量不到主導模型的差別。

### 3.2 每一題附的東西

`task.json`（prompt、tier 標註、timeout）、`fixture/`、確定性檢查、評分表（給模型評審）、人工評分選項（見 5.3），以及事先標註的
「這題原本該由哪個模型主導」。

### 3.3 鑑別力與題目篩選（事先寫定，避免看結果挑題）

- 新題目先用 opus 和 haiku 各試跑 1 次。**試跑結果不進正式資料。**
- 篩選規則只有一條：確定性檢查在原始 fixture 上必須失敗、在參考解（或 opus 試跑成品）上必須通過，證明檢查本身有效。
- **不因為 haiku 也通過就刪題**：易題保留，報告分「易／難／開放式」列出，讓讀者看到天花板效應在哪裡。

### 3.4 環境需求

C 類需要 Blender 4.5 LTS（Intel Mac 只能用到 4.5；5.0 起只支援 Apple Silicon），以環境變數 `BLENDER` 指定。
MCP 由本專案附的薄 MCP server 提供，每個工具呼叫跑一次 `blender -b --python`，不依賴需要開著視窗的第三方 addon。
渲染一律用 **Cycles、CPU、固定 samples**，禁止 Eevee：Cycles CPU 在任何機器上算出的畫面相同，只有速度不同。
開發機實測（640×360、3 盞燈、2 個物件）：Workbench 7 秒、Cycles CPU 64 samples 10 秒、Eevee 257 秒（無獨立 GPU）。
所有題目原則上在同一台機器跑；若必須換機器，同一題的所有組別必須在同一台機器上，時間指標依機器分開列。
D 類需要 Node 與 Remotion（版本鎖在 fixture 的 `package-lock.json`）。缺工具時該類題目跳過，報告註明。

## 4. 執行與隔離

### 4.1 每次執行

- 全新的 fixture 副本，在系統暫存目錄中。
- **暫存的 `CLAUDE_CONFIG_DIR`**：裡面只有該組別明確需要的 settings（hook）、agents、skills，沒有執行者的 plugin、hook、CLAUDE.md、MCP。
- **暫存的 `JEVCC_HOME`**：Jev 的紀錄寫在這裡，該次執行的 Jev 成本從這裡讀（不再讀 `~/.jevcc`）。
- 登入：`CLAUDE_CODE_OAUTH_TOKEN`（`claude setup-token` 產生，見 4.3）。
- **暫存的 `HOME`**：避免讀到執行者的 `~/.gitconfig`、shell 設定等，也避免 agent 在 `bypassPermissions` 下寫到使用者的家目錄。
- `--strict-mcp-config`，只給該題需要的 MCP server；`--setting-sources` 只留評測自己給的設定。
- **不上網**：所有題目都停用 `WebSearch`、`WebFetch`（研究題用附的資料集）。Remotion 的套件事先裝在共用的唯讀快取，
  每次執行從快取安裝，不連 npm。
- **推理強度固定**：每組都明確帶 `--effort`，數值在登記時寫定並記在環境清單中，不依賴各模型或 CLI 的預設值。
- **花費上限統一且寬鬆**：`--max-budget-usd` 每題同一個值，設在試跑最高花費的 3 倍；碰到上限或逾時的執行記為失敗，並另外列出次數，
  避免上限只截斷昂貴的組別而沒人發現。
- 同時執行數固定（預計 1，最多 2），記錄在環境清單；隨機排序的種子也記錄下來。
- 輸出用 `--output-format stream-json`：開頭的 init 事件列出實際載入的工具、MCP server、plugin、agents，**每次都存下來並檢查**；
  出現清單以外的項目就把該次執行標為「隔離失敗」，不計入結果。
- 每次保存：完整 transcript、成本 json、成品、檢查輸出。

### 4.2 有沒有照建議做

Jev 開的組別，記錄每次 Jev 給了什麼建議（往上、往下、review）、主導模型實際有沒有照做（從 transcript 讀，現有 `/jev stats` 的邏輯）。
Q2、Q3 的結果要搭配遵從率解讀：沒效果可能是建議不好，也可能是模型沒照做。

### 4.3 環境清單（每批寫一次，進報告）

Claude Code 版本、各模型 ID、jevcc commit、Jev 版本、Blender／Node／Remotion 版本、OS 與 CPU、執行日期、使用的帳號代號（不記帳號本身）。

### 4.4 帳號與用量

- 兩個 subscription 各產生一個 token，存在 repo 外、權限 600 的檔案；評測結束後刪除，並提醒使用者到帳號設定撤銷。
- 每批開始前檢查用量；遇到用量上限的錯誤就把該帳號標為暫停，換另一個帳號；兩個都暫停就等到重置時間。
- 結果逐筆附加到 jsonl；中斷後重跑會跳過已完成的（題目、組別、第幾次），所以可以分多個 5 小時時間窗跑完。
- 成本以 `total_cost_usd`（照定價計）＋ Jev 成本計。訂閱制實際消耗的是額度，報告會說明兩者的關係。

### 4.5 順序

同一批內題目 × 組別 × 重複次數隨機交錯，避免時段、快取或帳號差異集中在某一組。每次執行記下用的是哪個帳號，報告檢查帳號間是否有差異。

### 4.6 模型版本變動

評測可能橫跨數天。每次執行從 `modelUsage` 記下實際模型 ID；中途若有模型 ID 改變，前後分開報告，不混在一起算。

## 5. 評分

### 5.1 第一層：確定性檢查

通過／不通過。程式題只看這層。開放式題目這層不過就直接記最低分，不送評審。

### 5.2 第二層：模型評審（開放式題目）

- 評審模型：opus（ID 記錄在報告中）。
- **盲評**：評審只看到成品（影片抽影格與字幕、渲染圖與場景摘要、文件），看不到組別、模型、transcript。
- **兩兩比較**：同一題的兩個成品比「哪個比較好」，每對比兩次並交換順序，抵消位置偏差；兩次結論不一致就記平手。
- 評分表在登記時固定，跑完不改。
- 已知限制：opus 評審可能偏好 opus 的風格。用 5.3 的人工評分檢查。

### 5.3 第三層：人工評分（使用者）

- 每類開放式題目抽 5–10 組成品，盲評，順序隨機。
- 每題提供 5 個分數選項，每個選項寫明具體長相（依題目內容和成品設計），使用者只要挑一個，不用自己想標準。
- 評分頁是本機產生的 HTML，成品不上傳。
- 用加權 Cohen's kappa 計算人工與模型評審的一致程度；某類低於 0.6 時，該類的模型評審結果在報告中標為「不可靠」，只採人工評分。
- 預估工作量：約 40–60 份成品，每份 1–2 分鐘；可以分多次評，進度會保存。

### 5.4 評審成本

模型評審的花費另外列，不算進任何組別的成本。

## 6. 指標與統計

- 每組：通過率、品質分數、成本（Claude＋Jev）、**每完成一題的成本**、時間、回合數、各模型成本占比、派工次數、Jev 逾時次數。
- 與基準組成對比較：成本差與品質差，各附 bootstrap 95% 信賴區間。區間含 0 就寫「無明確差異」，不寫「節省」。
- 每類工作畫一張「品質對成本」圖。
- 重複次數：程式題 3 次；開放式題目先 3 次，若階段 1 顯示變異過大，階段 2 起改 5 次（這條規則事先寫定）。
- 結果不好、沒有差異的都照實列出。
- 每類題目只有 2–3 題時，類別層級的結論信賴區間會很寬，報告會寫明「這個樣本量能看出多大的差距」，不把小差距說成有差。

## 7. 可重現性套件（公開的內容）

- 本計畫與變更紀錄、所有題目檔（prompt、fixture、檢查、評分表、人工評分選項）。
- 原始 jsonl、每次執行的 transcript、init 事件、檢查輸出、環境清單。
- 成品：文件類全部收錄；影片與渲染圖檔案大，收錄雜湊值和抽樣，全部成品另外打包。
- 一個指令重跑：`jevcc bench --plan docs/eval-plan.md ...`（介面實作時定）。先 `--dry-run` 印出執行次數與依試跑估計的費用。
- 報告產生器：從原始資料重算所有數字，別人可以拿自己的 jsonl 產生同格式報告來比對。
- **用自己的題目量**：別人最在意的是「在我的工作上會不會一樣省」，這個問題我們的題目回答不了。所以提供題目格式說明和範本，
  讓使用者把自己常做的工作寫成題目、用同一套流程跑，得到自己的數字。報告會附「怎麼解讀、怎麼套用到自己的工作」一節。

## 8. 開發期間的隔離與還原

- 開發在獨立的 git worktree 進行；不跑 `go install`（不換掉使用者正在用的 jevcc），測試用的執行檔編譯到暫存路徑。
- 開發用的這個 Claude Code 對話開著 jevcc，不影響評測數字（成本只取每次執行自己的 `total_cost_usd` 與該 session 的 Jev 成本）。
- 開始前用腳本記錄 `~/.claude/settings.json`、`~/.claude/agents/`、`~/.jevcc/` 的檔案清單與雜湊；評測與開發結束後再比對一次，
  確認回到原狀，並刪除暫存目錄與 token 檔。比對結果收進報告。
- Blender 4.5.14 LTS 以 brew 安裝於 `/Applications/Blender.app`（使用者同意），評測結束後是否移除由使用者決定。

## 9. 費用、額度與時程

### 9.1 粗估（試跑前，誤差可能兩倍）

| 階段 | 執行次數 | 電腦時間（同時 1 個） | 照定價換算 |
|---|---|---|---|
| 1 | 約 290 | 約 25 小時 | 約 $300 |
| 2 | 約 480 | 約 45 小時 | 約 $500 |
| 3 | 約 150 | 約 25 小時 | 約 $300 |
| 模型評審 | — | 數小時 | 約 $50–100 |

單題時間假設：易題 0.5 分、難題 3 分、設計／規劃／研究 5 分、方向不明確與 Blender 10 分、影片 20 分。

### 9.2 額度（兩個 Pro 帳號）

- 真正的瓶頸是 subscription 額度，不是電腦速度；多台機器共用同樣兩個帳號，加機器不會增加額度。
- Anthropic 未公布 Pro 額度對應的用量，所以**不用定價推算次數**，改用試跑實測「每次執行消耗的 5 小時／7 日百分比」。
- 每個帳號每週保留 30% 給使用者平常使用，評測最多用到 70%。正式評測以 claude-2 為主（每週三 20:00 重置），
  main（開發用的對話所在帳號）只在 claude-2 暫停時使用。
- 2026-10-15 的狀態：main 5 小時 10%、7 日 35%（10/21 09:00 重置）；claude-2 未使用。
- 試跑先確認 Pro 方案在 Claude Code 中 opus 的可用程度。

### 9.3 優先順序（額度不夠時從後面砍，不看結果改順序）

| 順序 | 內容 | 回答 |
|---|---|---|
| P1 | 階段 1，非易題，每組 3 次 | Q1 |
| P2 | haiku＋往上、opus＋往下，非易題，每組 3 次 | Q2、Q3 |
| P3 | 階段 3，只跑 sonnet 主導 | Q4 |
| P4 | 易題（每組 1 次）、sonnet 的往上／往下／雙向、其他探索性組合 | 補充 |

試跑後依實測消耗算出每層所需額度，對照可用額度，向使用者報告能跑到哪一層、要幾週，同意後才開始正式執行。

## 10. 已定的選擇（2026-10-15）

1. 「往上」包含 Stop review，因為那是 jevcc 預設、使用者實際會得到的行為（見 2.1）。
2. 評審只用 opus，不加其他廠商的模型（使用者沒有其他訂閱）。opus 偏好自己風格的風險，靠 5.3 的人工評分檢查。
3. 成品全部公開。影片與渲染圖放 GitHub Release 的附件，不進 git（避免 repo 變大），repo 內只放雜湊值與連結。

## 11. 已知限制（報告中照列）

- `claude -p` 是單句、無人互動。真實的開放式工作通常有來回修改，這裡量的是「第一版成品」的品質。
- subagent 不能問使用者（平台限制），主導模型在 `-p` 模式下也無人可問；方向不明確的題目只能靠模型自己決定。
- 題目由本專案撰寫，可能有偏向；所以公開題目並提供「用自己的題目量」的方式。
- 開發機是 Intel Mac，渲染與 Remotion 的時間比一般機器長，時間指標僅供同一台機器內比較。
- Jev 的判斷不是每次都一樣，重複次數同時涵蓋了這部分的變異。
- 題目公開後可能進入未來模型的訓練資料，日後重跑的分數會偏高；報告註明題目公開日期。
- 隔離擋不掉 Bash 連網，也擋不掉帳號層級下載的設定（remote settings、policy limits）；後者記入環境清單。
- 開放式題目的確定性檢查只是門檻，試跑中便宜模型也幾乎全過；品質比較依賴評審與人工評分。

## 12. 結果怎麼用來改 jevcc

評測結果是改 jevcc 的依據，但看過結果後再用同一批題目量改過的版本，分數一定變好，可能只是對這批題目調出來的。規則如下：

1. **依據**：每個改動在 `docs/decisions.md` 新增一條，寫明依據的報告檔、比較組與數字（例如「haiku/up vs opus/off，規劃類，
   評審 2 勝 7 負」）。
2. **驗證用新題目**：改過的版本不以本計畫的 28 題當成效證明。驗證用沒看過的題目：另外撰寫的新題目，或使用者自己的工作
   （`docs/eval-howto.md`「用自己的題目量」）。新題目在看到改動後版本的結果之前寫定並 commit。
3. **同一批題目只當回歸檢查**：重跑本計畫的題目，只用來確認改動沒有讓原本做得到的事變差，不拿來宣稱改善。
4. **版本**：報告記錄每次執行的 jevcc commit；改動後的評測與本次評測分開報告，不合併計算。

對應關係（本次結果預計影響的決定）：Q1 → D2（哪類工作建議哪個模型主導）；Q2 → 往上派工的門檻與價值；
Q3 → 往下派工是否預設開啟；Q4 → D3（`jev-*` 的工具設定）；試跑觀察（開放式工作 Jev 不升級）→ handoff 的
「session 開頭判斷開放式工作」點子。
